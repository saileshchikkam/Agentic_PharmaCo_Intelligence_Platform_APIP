# Proposed ADR domain and database

Status: design only. Existing database evidence and restrictions: [audit](00-repository-audit.md). API types: [contracts](03-api-and-agent-contracts.md).

## Storage choice

Use the **existing local SQLite database and Node connection**, with additive ADR tables and prepared statements. Do not create a second identity database or require hosted Supabase/Postgres/vector infrastructure during the ten-day prototype. Keep the database outside Git and synchronized source folders, on a local disk. Enable foreign keys on every connection; use short transactions, WAL and bounded busy handling. SQLite WAL allows concurrent readers but a single writer; it requires processes on the same host and does not work across a network filesystem ([official WAL documentation](https://www.sqlite.org/wal.html)). Provider calls must run outside write transactions.

This is an implementation recommendation for a local fictional demo. A later public/hosted build needs a distinct authentication/deployment decision and tested PostgreSQL migration; the existing Supabase profile bootstrap does not supply ADR tables or backend session verification.

## Authoritative data model

Two counters avoid accidental invalidation: `revision` increments for each case command (including state/assignment changes); `content_version` increments only when statements, structured fields, confirmations or profile imports change. Each content version is immutable. Agent artifacts/reviews cite `(case_id,content_version)`; persisting an execution result does not bump case revision. Lifecycle changes without content changes do not stale evidence. New content always invalidates current validation/analysis/review applicability, while historical artifacts remain queryable and labeled stale.

Data planes:

1. **Original statements:** exact narrative/field text and source revision, never overwritten. Corrections append a new statement with `supersedes_id`.
2. **Proposals:** untrusted execution artifacts, each with quote/span, source statement and intended path. Never used by queries/export as confirmed facts.
3. **Confirmed fields:** a user-confirmed or explicitly entered value plus field-origin record. Manual entry requires explicit confirmation; saving an unfinished form does not automatically confirm it.
4. **Review conclusions:** immutable human decisions/notes attributed to a verified account/role/grant and exact content version. They never rewrite original statements or acquire human clinical authority from an AI summary.

Missingness is `provided | unknown | not_asked | not_applicable`; missing values have `value:null`. A provided `false` or zero is valid. Empty strings are not equivalent to a known negative. Preserve original strings before any normalization. An explicit negative has `provided` plus the appropriate `false`/negative statement, not `unknown`.

Dates use `{text, iso, precision}`; `iso` may be `YYYY`, `YYYY-MM` or `YYYY-MM-DD` as permitted by precision, or null for relative text. Do not silently invent day/time/time zone. Event timing relative to medicine is descriptive and not causal. Intensity, reported seriousness, outcome and reviewer conclusion are distinct fields; unknown seriousness is never `false`.

## Proposed records and relationships

All new identifiers are server UUIDv4 strings; timestamps are server UTC ISO-8601 strings. `*_json` requires valid JSON and runtime schema validation. FKs default RESTRICT; deliberate purge is out of MVP. All mutable aggregate roots have `created_at`, `updated_at`, `revision`; immutable child records have `created_at` and source version. Below are minimum columns, constraints and indexes, not an executed SQL migration.

### Identity and access

- Reuse `local_users(id, email, salt, password_hash)` and `local_sessions(token_hash,user_id,expires_at)` unchanged in meaning. Never return password/session material in ADR views.
- `adr_user_roles(user_id FK local_users, role CHECK reporter|reviewer|operator, provisioned_by FK local_users nullable for initial CLI bootstrap, created_at, revoked_at)`, PK `(user_id,role)`. Reporter default is a policy baseline; reviewer/operator are server provisioned, never signup metadata. Index `(role,revoked_at,user_id)`.
- `adr_case_grants(id UUID UNIQUE NOT NULL, case_id FK adr_cases, user_id FK local_users, permission CHECK review, granted_by FK local_users, created_at, revoked_at)`, PK `(case_id,user_id,permission)`. Index `(user_id,revoked_at,case_id)`. The unique UUID is the API grant ID; regrant reactivates the row with a fresh audit event. Reviewer access requires both active reviewer role and active case grant. Operator has no implicit case access. Reviewer must differ from case owner for approval.

### Cases, content and source records

- `adr_cases(id PK, owner_id FK local_users, fictional_only CHECK=1, language CHECK en|te|mixed|und, status, content_version INT>0, revision INT>0, created_at, updated_at, archived_at nullable)`. Index `(owner_id,archived_at,updated_at,id)` and `(status,updated_at,id)`. Content-version pointer validated transactionally after version creation; ADR-1 must avoid a circular-FK initialization deadlock.
- `adr_case_versions(case_id FK adr_cases, version INT>0, author_id FK local_users, snapshot_json, snapshot_sha256, schema_version CHECK=1, created_at)`, PK `(case_id,version)`. Snapshot contains reporter/patient fictional context, narrative refs, medicine/event IDs and confirmed fields. Hash computed from canonical serializer bytes, not arbitrary object-key order. Immutable ledger is the export source of truth.
- `adr_statements(id PK, case_id FK adr_cases, introduced_version, author_id FK local_users, source CHECK reporter|profile_import|medassist_import, source_ref_json nullable, text, language, supersedes_id nullable, created_at)`. Composite FK `(case_id,introduced_version)` to versions, composite unique `(case_id,id)`; supersedes must belong to same case. Index `(case_id,introduced_version,id)`. Import reference contains consent action and source revision, never an unrestricted external pointer.
- `adr_medications(case_id, content_version, id, position INT>=0, role CHECK suspect|concomitant, name_json, dose_json, route_json, frequency_json, started_json, stopped_json, indication_json)`. PK `(case_id,content_version,id)`, FK case/version, unique `(case_id,content_version,position)`. IDs stable across content versions where the same entry persists. All field JSON uses `DraftField<T>` with explicit confirmation state; no terminology code inferred from text.
- `adr_events(case_id, content_version, id, position, description_json, onset_json, intensity_json, seriousness_json, outcome_json)`. Same PK/FK/position rules as medicines. Seriousness consists of separate missing-aware reported booleans for death, life-threatening, hospitalization, disability, congenital anomaly and other reported serious outcome; these are reporter statements, not a classifier result. No unreviewed urgent-care routing is added.
- `adr_field_origins(case_id, content_version, path, origin CHECK manual|accepted_proposal|edited_proposal|confirmed_import, statement_id nullable, proposal_execution_id nullable, proposal_id nullable, confirmed_by FK local_users, confirmed_at, source_span_json nullable)`. PK `(case_id,content_version,path)`; FK case/version; same-case checks for statement/execution. Confirmations can carry forward unchanged fields with original confirmer/time plus source-version reference; edited fields require new confirmation.

Medicine/event rows are normalized query projections of each immutable snapshot; snapshot and projections are inserted in one transaction and reconciled in tests. Do not implement independent mutable JSON and table truths. A content patch writes a complete new snapshot and its projections, leaving old projections intact. Cap case at 20 medicines, 20 events and 20 field proposals per run to bound prototype storage/UI.

### Executions, findings and evidence

- `adr_executions(id PK, case_id, content_version, stage CHECK reporting|validation|knowledge|analysis, input_hash, config_hash, corpus_version nullable, status, mode CHECK provider|deterministic|manual_required, attempt_count, max_attempts CHECK 1..2, parent_id nullable, requested_by FK local_users, lease_until nullable, cancel_requested_at nullable, output_json nullable, error_code nullable, provider_id nullable, model_id nullable, prompt_version nullable, schema_version, started_at nullable, finished_at nullable, created_at)`. FK case/version; unique `(case_id,id)`; indexes `(status,lease_until,created_at)` and `(case_id,content_version,stage,created_at,id)`. No raw secret/request headers in artifacts. Prompt registry stores templates/hashes, not credentials. ADR-4 can add run-group metadata in the same migration if needed; no general DAG engine.
- `adr_validation_findings(id PK, execution_id FK adr_executions, rule_id, path, severity CHECK blocker|warning|info, code, message_key, observed_json nullable, created_at)`. Index `(execution_id,severity,id)`. Execution binds the exact case version/rules version. Findings are not mutable manual overrides; reviewer acknowledgement is a separate decision.
- `adr_knowledge_documents(id PK, source_key, source_version, title, publisher, canonical_url, jurisdiction, language, published_at nullable, retrieved_at, content_sha256, permitted_use, rights_evidence_url, rights_reviewed_by FK local_users, rights_reviewed_at, clinical_review_status CHECK pending|approved|not_clinical_fixture, approved_by nullable, approved_at nullable, withdrawn_at nullable, corpus_version, created_at)`. Unique `(source_key,source_version,content_sha256)`; index `(corpus_version,clinical_review_status,withdrawn_at,id)`. Publication/review dates unknown remain null. Fixture documents cannot masquerade as clinical references.
- `adr_knowledge_chunks(id PK, document_id FK documents, ordinal, section, page nullable, start_offset, end_offset, text, content_sha256, token_count, created_at)`. Unique `(document_id,ordinal)`; indexes `(document_id,id)` and document FTS mapping. Immutable source offsets are Unicode code-point offsets, separate from JS statement-span offsets.
- `adr_chunks_fts` FTS5 virtual index of approved chunk text/title and a chunk ID mapping; rebuildable projection, never authoritative evidence. Join back to approved/nonwithdrawn document registry before returning results. Use bound literal query terms; no user-controlled SQL or FTS operators.
- `adr_citations(id PK, execution_id FK knowledge execution, case_id, content_version, chunk_id FK chunks, document_hash, chunk_hash, rank INT>0, score REAL, quote, quote_start, quote_end, created_at)`. FK case/version and same-case execution check; unique `(execution_id,chunk_id,quote_start,quote_end)`; index `(case_id,content_version,execution_id,rank)`. Score is retrieval rank evidence, not medical confidence.

### Review, workflow, audit and exports

- `adr_proposal_decisions(id PK, case_id, source_content_version, execution_id, proposal_id, action CHECK accept|edit|reject, decided_value_json nullable, decided_by FK local_users, resulting_content_version, created_at)`. Unique `(execution_id,proposal_id)`; same-case composite checks; index `(case_id,resulting_content_version)`. A batch decides all selected proposals transactionally and creates at most one new version. Old undecided proposals become stale after any version edit; request a fresh run rather than accepting them against changed text.
- `adr_review_decisions(id PK, case_id, content_version, reviewer_id FK local_users, decision CHECK approve_academic|request_changes|comment, notes, acknowledged_finding_ids_json, acknowledged_limitations_json, validation_execution_id, retrieval_execution_id nullable, analysis_execution_id nullable, created_at)`. FK case/version, same-case artifact references; index `(case_id,content_version,created_at,id)`. Approval requires current validation and explicit missing-evidence/analysis acknowledgement; no clinical sign-off field in MVP.
- `adr_audit_events(id PK, case_id nullable FK cases, content_version nullable, actor_id nullable FK local_users, actor_kind CHECK user|worker|operator, action, resource_type, resource_id, correlation_id, before_hash nullable, after_hash nullable, metadata_json, created_at)`. Index `(case_id,created_at,id)`, `(correlation_id,id)`. Append-only application interface; content hashes/diff paths instead of duplicating narratives. Role/grant operations with no case still audit. Failure to write required audit rolls back the associated change. No tamper-proof compliance claim.
- `adr_idempotency(actor_id FK local_users, route, key, request_hash, status CHECK pending|complete, response_status nullable, response_json nullable, resource_id nullable, expires_at, created_at)`. PK `(actor_id,route,key)`; index `(expires_at)`. Replay only after current session/resource authorization. Key TTL 24 hours for commands; long-term case/run uniqueness is independently enforced.
- `adr_export_receipts(id PK, case_id, content_version, actor_id FK local_users, format CHECK json|html, template_version, content_sha256, review_id nullable FK reviews, created_at)`. FK case/version; index `(case_id,content_version,created_at,id)`. Generate bytes from immutable data; no public URL or persistent file needed. A receipt says generated, not received by a regulator.
- `adr_schema_migrations(version PK, checksum, applied_at)` tracks ADR schema independently of the existing account `PRAGMA user_version=2`. Reject unknown future versions/checksum changes; never repurpose an older account schema version.

## Cross-record integrity and permission rules

Every nested read/write joins its case and policy scope. Child UUID possession grants nothing. Composite `(case_id,version)` FKs and `(case_id,id)` uniqueness prevent attaching another case's statements/artifacts. Where SQLite cannot express a relationship with a simple FK (for example an execution's required stage), use a checked transaction plus negative tests; do not assume TypeScript prevents bad writes. References in JSON require explicit runtime resolution.

Reviewer edits are correction requests/notes; only owner-confirmed corrections alter reported facts. Case grant creation requires an owner request naming an already server-provisioned reviewer; role grants remain operator-only. Revocation applies immediately, including worker result publication. Operators can manage corpus/roles but need a separate case grant and reviewer role to inspect case data.

## Additive migration strategy — execute only in ADR-1

1. Verify current checkout, account version 2 and runtime. Read role/session seam tests before edits. Back up fictional development database using a consistent SQLite backup/closed connection, not a live file copy ignoring WAL. Test restore against a separate temporary file.
2. Add `database/adr/migrations/001-foundation.sql` and a runner with checksum/version checks, `BEGIN IMMEDIATE`, foreign-key verification and rollback. Start with roles/grants, cases/versions/statements/medicine/event/provenance/audit/idempotency; later phase migrations add agent/evidence/review tables. Do not execute SQL in ADR-0.
3. Keep existing account tables and old draft APIs functional. No automatic browser/account-draft import. Proposed explicit import endpoint maps four legacy statement values to original source text; legacy `user-confirmed` is recorded historically but is not wholesale confirmation of a new schema.
4. Import receipt uniquely identifies `(owner_id,legacy_draft_id,legacy_revision)` in a proposed `adr_legacy_imports` table with `case_id` FK and `created_at`; preserve the old draft. Confirm mapping in the UI. Unknown dose/onset remain unknown; no automatic profile copy.
5. Test empty install, version-2 upgrade, duplicate import, interruption/failure, too-new schema refusal, exact text, cross-account denial and account/profile compatibility. Apply first to disposable fictional data.
6. Rollback uses feature disable and old-compatible code while retaining additive tables. If restoration is necessary, stop writers, preserve the failed DB separately and restore the verified backup. Never delete existing drafts or run destructive down-migrations over new case data.

Retention: no automatic purge or account cascade of ADR history in the MVP. Archive is reversible; real retention/deletion/consent/backup policy needs separate approval before real data. New reports never enter the knowledge corpus or a training dataset automatically.
